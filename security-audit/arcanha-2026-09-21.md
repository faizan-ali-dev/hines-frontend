# Arcanha external security review — 21 September 2026

## Confirmed finding: reflected cross-site scripting on login

- Target: https://arcanhaofficial.com/account/login
- Parameter: `from_page` (GET query string)
- Authentication required for reproduction: none
- Status: HTML injection and JavaScript execution confirmed in the browser.
- Test window: approximately 07:31–07:33 UTC, 21 September 2026 (12:31–12:33 Pakistan time).
- No credentials, session tokens, or private customer records were read by the proof. No data was sent to an external collection endpoint. No account or production record was changed.

### Evidence

An inert HTML marker supplied in `from_page` appeared as a real `<b>` element inside the login form. The returned DOM included:

```html
<input type="hidden" name="from_page"><b data-audit="928">marker</b>"&gt;
```

A second request used the following harmless decoded parameter value:

```text
/account/"><svg onload="document.documentElement.setAttribute('data-audit-xss','confirmed927')"></svg>
```

The browser parsed this element in the login form:

```html
<svg onload="document.documentElement.setAttribute('data-audit-xss','confirmed927')"></svg>
```

After the page loaded, a read-only DOM inspection returned:

```json
{
  "executionMarker": "confirmed927",
  "svgPresent": true,
  "title": "Login"
}
```

The initial immediate inspection returned a null marker; the later inspection confirmed execution after the load event. The inspection itself did not execute the proof or set the marker.

### Controlled reproduction

Use an isolated, logged-out browser. URL-encode the harmless parameter above and append it as `from_page` to `/account/login`. After loading completes, inspect the root HTML element for `data-audit-xss="confirmed927"`. No account login is needed. Navigate back to the ordinary login URL afterward.

### Impact and limits

The demonstrated flaw lets a crafted login URL execute attacker-controlled JavaScript within the site's origin when someone visits it. It could alter the login form or capture credentials entered on that page. Potential access to authenticated data depends on victim session state, route behavior, and account privileges; that was not tested.

This is a confirmed vulnerability, not proof that it caused the reported disclosure of all registered-user information. There is no demonstrated database dump, cross-account record access, administrator compromise, or historical attacker attribution in this review.

### Remediation proposal (not deployed)

Review the PHP rendering of the `from_page` hidden field. Its observed behavior is consistent with request data being placed into an HTML attribute without proper contextual encoding. The exact PHP implementation has not been inspected.

1. Accept only an explicit allowlist of legitimate internal return destinations, ideally represented by server-side route identifiers. Reject unexpected types and destinations; do not accept arbitrary external URLs.
2. When rendering the validated destination into a quoted HTML attribute, encode it using `htmlspecialchars($returnPath, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8')`.
3. Apply return-destination validation again wherever the value is used for a redirect. HTML escaping and redirect validation address different contexts.
4. Replace registration's insertion of `data.message` into `innerHTML` with text-node construction or `textContent`; keep intended static markup separate.
5. Add a restrictive Content Security Policy as defense in depth after checking compatibility with legitimate scripts. Do not rely on WAF filtering as the application fix.
6. Retest the inert HTML and JavaScript markers and legitimate login redirects. The marker must not become an element or execute.

## Remaining work

- Two disposable synthetic accounts are needed for controlled cross-account authorization tests.
- PHP handlers and server-side access-control code have not been supplied or inspected.
- Preserve and correlate incident-time access logs, authentication events, application logs, and available Cloudflare events to determine whether this XSS or another route was used.
- Search retained logs for suspicious `from_page` values, accounting for URL encoding. Absence of a matching entry is not proof the flaw was never exploited.
- Compare any attacker-provided evidence with actual database fields and timestamps without reproducing customer PII in the report.

## Client-ready message

We confirmed a security vulnerability on the website's login page. The `from_page` URL parameter is inserted into the page without adequate HTML escaping, allowing a crafted link to execute JavaScript in a visitor's browser. We verified this with a harmless page marker, without accessing customer records or changing accounts.

This could be used to manipulate the login form or compromise credentials entered after following a malicious link. We recommend prioritizing a fix that validates return destinations and safely encodes the parameter before rendering it.

We have not yet established that this vulnerability caused the reported user-data disclosure. We will need controlled account-access tests and incident-log review to confirm that connection and determine the scope. The vulnerability has been identified and reproduced; no production fix has been deployed during this review.
